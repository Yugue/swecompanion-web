## Guardrails and permissioning

Guardrails check inputs, proposed operations, and outputs. Critical permission rules need runtime enforcement.

## 1. Three placements

```text
input checks → model loop → output checks
                    ↓
            tool validation/authorization
```

Checks can be deterministic or model-assisted; distinguish their guarantees.

## 2. Prompt versus enforcement

“Refund no more than the total” guides the model.

The backend checks ownership, remaining refundable amount, currency, policy, and preconditions before executing.

Use explicit errors, transactional checks, and idempotency rather than relying on a language instruction.

## 3. Least privilege

Scope tools and credentials to required records and operations.

Authorization uses authenticated session identity, not an identity field generated by the model.

## 4. Consequential actions

Choose controls using impact, reversibility, data sensitivity, and policy.

Low-impact reversible work may execute after validation. High-impact actions may require a reviewed proposal. Bind approval to the exact operation and relevant state.

## 5. Resource limits

Bound run steps, time, usage, tool failures, and tenant spend.

Define partial-result or escalation behavior on exhaustion.

## 6. Output checks

Validate schema and meaning, source support, data scope, and action-claim consistency.

A successful tool request alone does not prove the claimed effect occurred.

## 7. Unavailable checks

If a required permission/policy check cannot evaluate, stop that operation.

Specify which safe investigation can continue and what evidence accompanies escalation.

## 8. Test without the model

Submit another user's ID, excessive amounts, stale approval, duplicates, malformed data, and missing prerequisites directly.

Also test unavailable validators and expired credentials.

## What matters most

> The gate must hold even when the caller proposes an invalid operation.
