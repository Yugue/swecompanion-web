## ReAct: interleaving reasoning and acting

ReAct is the default agent pattern: a short thought, one action, one observation, repeated. Its strength is that every decision is made against **fresh evidence from the world**, which is what keeps a model's planning honest.

### 1. The cycle

```text
Thought:      I need the order date before I can apply the 30-day rule.
Action:       get_order(id="48812")
Observation:  {"placed": "2026-03-02", "total": 240.00, "status": "delivered"}
Thought:      Placed 2 March, today is 19 March - inside the window.
Action:       get_policy(clause="refund_window")
Observation:  {"days": 30, "exceptions": ["final_sale"]}
Thought:      Need to check final_sale on this item.
Action:       ...
```

The thoughts are short and about the **next** decision. Long essays between actions are a sign that the agent has stopped using the environment.

---

### 2. Why grounding matters

```text
pure reasoning:   plan built entirely from priors
                  → confident, coherent, and wrong when reality differs

pure acting:      call, call, call
                  → no accumulation; a surprising result changes nothing

ReAct:            reason about the last observation, then act again
                  → plan is corrected by evidence at every step
```

The observation is the only part of the loop that is not generated by the model. That is why interleaving beats reasoning alone on anything involving real systems.

### Rule of thumb

> An observation that doesn't change the next thought means the agent is not actually reading it.

---

### 3. Against plan-then-execute

| | ReAct | Plan-then-execute |
|---|---|---|
| Adapts when step 3 invalidates step 1 | Naturally | Only with explicit replanning |
| Human can approve the plan first | No - there is no plan | Yes |
| Parallelizes independent work | Poorly - one action at a time | Well - the plan shows independence |
| Cost | Higher: a model call per action | Lower per unit of work |
| Failure mode | Wandering | Executing a stale plan |

The honest summary: ReAct is robust and myopic; planning is efficient and brittle. Hierarchical designs use a coarse plan with ReAct inside each step.

---

### 4. The myopia failure

Every individual step is locally reasonable, and the run still fails:

```text
step 4:  search "refund policy"        reasonable
step 7:  search "refund policy 2026"   reasonable
step 11: search "returns window"       reasonable
step 15: search "refund eligibility"   reasonable
                                       → 15 steps, no answer, all defensible
```

Nothing in the pattern asks "is this working?" Fixes are structural: a step budget with a mandatory checkpoint ("summarize what you know and what's missing"), a repeated-call detector, and a tool that can return a definitive "not found."

---

### 5. Practical notes

- Keep thoughts to one or two sentences; they are re-sent on every later turn.
- Allow parallel actions in a single turn when they are independent - ReAct does not require one call at a time.
- Put the observation in a compact, typed form; raw payloads make the next thought worse, not better.

---

## What matters most

- **Thought → Action → Observation, repeated.** The observation is the only part of the loop the model did not generate, which is what keeps planning honest.
- **It beats pure planning when reality disagrees with the plan,** and beats pure acting because a surprising result actually changes the next decision.
- **Its weakness is myopia:** every step is locally sensible and the run still wanders for fifteen steps without converging.
- **Fix that structurally** - a mandatory mid-run checkpoint stating what is known and what is missing, a repeated-call detector, and tools that can return a definitive "not found".
- **Keep thoughts to a sentence or two,** since they are re-sent on every later turn, and allow parallel actions when they are genuinely independent.
